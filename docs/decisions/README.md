# Architectural Decision Records (ADRs)

ADRs capture significant technical decisions, along with the context and consequences. Add an ADR when a choice meaningfully impacts architecture, operations, or developer experience.

## When to add an ADR (TBD)
- Introducing a new service/component or retiring one
- Selecting major technologies (e.g., framework, database, queue)
- Defining cross-cutting concerns (auth, observability, error model)
- Changing protocols or public APIs

## ADR Template (copy into a new file under `docs/decisions/`)

```
# Title (TBD)

- Status: Proposed | Accepted | Superseded | Deprecated | Rejected
- Date: YYYY-MM-DD
- Authors: @handle(s)
- Related: links to issues/PRs/ADR IDs

## Context
TBD: Background, problem statement, constraints, and options considered.

## Decision
TBD: The decision made and rationale.

## Consequences
TBD: Positive, negative, and neutral outcomes; follow-ups and migrations.
```
